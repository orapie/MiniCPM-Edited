# 角色卡回答人称修复计划

日期：2026-11-04  
状态：阶段 0–3 的计划内工程及精简验证已完成；自动确定资料说话者和第二人称指代仍未实现，真实模型样本存在误答，最终版本未做再次生成验证。  
目标：在 `CHARACTER_RAG` 中，对当前及以后接入的所有角色卡通用地减少模型沿用参考资料的第一、第二、第三人称造成的角色视角错乱，让角色从自己的立场回答；保留对其他人物、玩家、引文及正常自我介绍的表达。罗辑和史强仅为解释性示例，不是实现条件或默认角色。

## 一、当前实现与问题定位

1. 源模板是 `app/src/main/assets/prompts/roleplay_system.prompt`，由数据库安装流程复制为 `<filesDir>/program/prompts/roleplay_system.prompt`。模板已经写有“不要旁白”，也已加强涉及自身经历、想法和行动时使用第一人称的要求。因此问题不能只归因于缺少第一人称指令：模型可能忽略指令，检索文本的原文叙述也可能影响输出；没有该轮实际请求与生成记录时，后一项只是待验证的可能原因。
2. `CharacterRagPromptBuilder` 把经过筛选和截取的原文作为 user 侧“本轮检索资料”，提示它不是指令或角色亲身记忆。素材可能有“罗辑……他……”等第三人称叙事，模型可能沿用叙述人称。但资料在 user 而非 system，不能将其误写为已获角色知情授权，也不能据此断言示例一定由 RAG 引起。
3. 角色输出由 `MainActivity.generateBufferedRoleplay()` 缓冲，经 `RoleplayGenerationCoordinator.resolve()` 调用 `RoleplayOutputGuard.evaluate()`；通过后才显示并持久化。`RoleplayLeakClassifier.selfNarrationPattern()` 当前仅检查当前角色名后紧邻“沉默、转身、抬眼、皱眉、心想、说道、说、答道、开口”等少量词。示例“罗辑一直在思考，他决心……”不符合该模式。
4. 更关键的是，即使匹配上述模式，`POSSIBLE_SELF_NARRATION` 当前也只是 `WARNING`。guard 只对 `HIGH` 触发 `RetryWithRepair`，因此这类 warning 仍会作为 `Accept` 展示并可能写入会话。不能只扩充正则而不调整决策。
5. 现有修复重试最多一次，追加的通用指令已有“只直接用角色第一人称回答玩家”。重试仍失败时显示“这话我一时说不清。”；被拒绝文本不应展示或保存。`RoleplayOutputObserver` 与 guard 共用分类器，`roleplay_observation` 可记录信号与决策。回答能力 gate 可能直接返回固定回复，该路径与正常模型生成需要单独区分。

### 补充：资料视角与对话视角不同

用户观察到参考资料中的“你手上的是一个芯片”可能诱导模型输出“你应该是一个有特殊身份的人”。这是值得重点验证的视角混淆：资料中的“你”可能指当前角色、其他人物或原对话中的听话者；聊天回答中的“你”通常指玩家。模型如果不区分上下文，就可能把针对角色的资料变成针对玩家的判断。**仅凭这两个片段不能确定原文的说话者和被指向者，也不能证明它们导致了这次输出**；需要结合原文上下文和本轮请求复核。答案中的“你”也可能本来就是正确称呼玩家，不能一律禁止第二人称。

当前实现通过 `CharacterRagPromptBuilder.build()` 将 `[资料 N]` 原文和“玩家：当前问题”共同放进 user 消息；system 附加说明资料可供参考，但不等于角色亲身记忆，也不是指令。`compileContext()` 基于当前问题的词项匹配挑句，每条主体最多约 130 字、总资料预算 600 字；相邻句可能因为预算未被保留。因此引文的说话者、被询问者或代词先行词可能缺失，资料块本身也没有明确的叙述主体字段。以上是代码可见的风险，不代表具体回合一定发生了截断或主体误判。

当前 `roleplay_system.prompt` 已要求自述用第一人称、不模仿第三人称旁白，但没有明确说明**资料里的第一、第二人称分别属于谁**。`RoleplayOutputGuard` 的 `possible_self_narration` 只观察少量“角色名＋动作”并且是 warning；现有规则没有通用的“资料中的你误指当前角色”识别。因此单纯继续强化“第一人称”或增加 `你` 黑名单都不足以解决这个问题。

### 优先修改方案：先保留视角，再回答

1. **先建立可核对的资料上下文。** 保留原始 evidence ID、原文、所选 UTF-16 区间、来源行和角色/cutoff，按完整原文及上下句判断引文是否有明确说话者、听话者和主语。取证时的判断应标记为 `明确/未知` 并附依据；现有索引没有可靠的逐句说话者标注，不能假设自动判断恒正确。预算内优先保留能消解指代的原句与相邻句，无法确定时标为未知或不采用该细节，而非猜测“你=角色”。
2. **改资料包装，不改源文。** 在 `CharacterRagPromptBuilder` 的资料说明中，用短句说明“资料中的我、你、他依原文说话者和听话者理解，不自动对应本轮玩家；回答时你是当前角色，玩家才是本轮的你”。对清楚知道主体的资料，可附数据来源允许的主体提示；不清楚就显式标记“原文指代未确定”。继续使用 user 侧不可信参考，不改写原文，不将素材直接升格为 system 事实或亲身记忆。
3. **仅对高置信度信息构造受控的视角提示。** 如有可靠来源和可追溯的身份映射，可在单独的本轮辅助字段说明“该句中的‘你’指当前角色”，但不得自动将原句机械替换为“我”。为每一条提示关联 evidence ID 和原文跨度；若来源、主体、角色知情、时点、指代任一不明确，则不生成确定性提示。引用、旁白、多人交谈、嵌套引号及转述都要独立考虑。
4. **让模型回答而不是复述资料措辞。** 不预设“你”必然等于角色、也不强制每句带“我”。建议在本轮参考说明中添加：“参考内容有人物之间的对话或旁白；先根据原文确认说话者和对象，再从当前角色立场回答。原文对象不明时不要猜测。”短指令应与现有 system 规则一致，且不将引用文本当作新指令；保持用户问题原样、素材原文和信任边界。
5. **最后才做输出防线。** 扩展 guard 对清晰的当前角色第三人称旁白触发一次重试；第二人称只在有高置信度目标解析、并能确认回答把角色自身属性错误归给玩家时才考虑重试。无可靠主体信息时只观察，不把“你手上的芯片”或“你问得对”自动认定错误。重试要继续携带同一证据与 cutoff，不拼入不可信的被拒回答，不修改玩家原问题或跳过回答能力 gate。

## 二、目标与边界

- 识别**叙述当前角色本人**的高置信度第三人称旁白，要求重新生成，而不将其他人物的“他/她”一概视为错误。角色名与可靠别名从当前已验证角色卡的 `identity.name`、`identity.aliases` 取得并贯穿本轮；歧义时保守处理，不能硬编码任何具体角色。
- 自然的第一人称自述、无主语的口语、说明第三人、引用历史原话、书名、别人对角色的称呼都应该可通过。要求人称正确并不意味着每句都必须出现“我”。
- 不把“罗辑”统一替换为“我”，也不把所有“他”替换为“我”；这样会破坏引文、第三人及句子逻辑。不得把未审核参考内容升级为角色已知事实，也不能用修复放宽数据库 cutoff、认知授权或未知处理。
- 未明确指代的“他”不能只凭代词推定为当前角色。宁可把不确定的情况记录为 warning，也不要错误拦截“史强帮了我，他很可靠”。本方案不能保证穷尽自然语言所有叙述形式。
- 保持现有 RAG/OFF 模式行为；不更改普通模式的流式输出，不改数据库、会话、模型资产及检索策略。

### 通用角色卡及新增角色接入要求

1. **单一身份来源。** 每轮从当前已绑定并验证的数据包与选中角色卡取得 `npcId`、`identity.name`、`identity.aliases`，形成本轮不可变的角色身份上下文，明确传给资料视角处理、prompt、输出 guard、observer 和重试。当前 `MainActivity` 已从当前角色取显示名，但现有 guard 接口只接收一个 `characterName`；需扩展现有调用链，不能假设别名当前已传入。日志和数据记录中的稳定身份使用 `npcId` 及数据库 fingerprint，不以显示名代替角色 ID。
2. **无需为新卡增加名单或代码。** 通用模板、资料说明和检测逻辑均以本轮角色身份为参数；不得硬编码 `luo_ji`、罗辑、史强或某部作品的称谓。未来角色卡遵循当前数据包和角色卡加载契约后，按其名字及可靠别名自动生效；本计划不引入新数据库格式或要求维护针对每个角色的规则表。
3. **同名、别名和缺失均保守处理。** 名称/别名仅使用非空、去重且可靠的卡内值，对正则特殊字符做安全转义；若为空、为泛称、与其他角色重名/重别名，或资料主体不明确，不将其单独作为高置信度证据，可降为 warning 或跳过该规则。不得使用 `npcId`、占位字符串或另一个角色的名字假装当前角色名；保留原有 system 约束并在诊断中记录原因。若显示名不可用，应从当前验证卡重新获取或安全地跳过姓名检测，不阻止其他独立 guard 规则。
4. **切换与作用域。** 角色切换、数据包/fingerprint 更新或新回合开始时，从该回合实际绑定重新构造身份；如缓存任何解析结果，键至少包括 dataset fingerprint、`npcId` 及角色卡版本/内容标识，并在更换数据包或角色时失效。活动回合继续使用自身固定身份，避免上一角色的姓名、别名或证据作用于下一角色；不依赖旧会话的角色名。所有证据仍需按当前角色及 cutoff 检查。
5. **指代可解析才采用。** 原文说话人、听话人和其姓名/别名须从当前数据库中可追溯的上下文确认；角色卡别名本身不证明某条资料的“你”指向谁，更不证明角色知情。多人对话、重名、引用和未标注场景保持未知，不生成确定性的主体提示，也不自动升格为角色知识。
6. **少量通用性回归。** 在同一个定向测试中使用两个合成角色卡 A/B：A 的姓名或可靠别名作自我旁白应触发对应规则；切到 B 后，A 作为第三人应被允许、B 的自我旁白应按规则处理。再用一个空名、歧义别名或带正则特殊字符的例子覆盖保守行为。测试数据只作 fixture，不必给每张真实角色卡逐一运行测试，不需增加对话模型或设备矩阵。

## 三、分阶段实施

### 所有阶段的测试约束

- 按用户要求，每完成一步只做与该步直接相关的**少量测试**：通常选择 2–3 个有区分度的正反例，使用一个最相关的定向测试类或命令，不默认运行完整测试集、全角色矩阵、全设备矩阵或多模型测试。
- 前一步已验证且本步未修改的行为不重复检查；遇到失败时先修复并仅重跑失败项或受影响的定向集合。只有出现新的失败或尚未解决的具体风险时才扩大范围，并说明原因。
- 阶段 0 以只读检查和已有失败记录为主；阶段 1 检查少量模板/预算与资料包装；阶段 2 检查少量人称正反例和一次重试；阶段 3 合并做一次精简构建与可用设备冒烟。各阶段的具体上限和未覆盖项按下文执行。
- 不为凑数量重复生成或多次运行相同检查；复用已有结果。设备不可用时完成可运行的定向测试并如实记录设备部分未验证，不测试其他对话模型。

### 阶段 0：记录失败样例和现有行为

1. 固定当前 Debug APK、数据库 fingerprint、当前角色、cutoff、当前模型和生成参数；可用现有罗辑“雪地工程的目的是什么？”作为示例，但不得依赖该角色。记录 `RAG_TRACE`、首个 `BACKEND_REQUEST`、实际可见回答和 `roleplay_observation`；如果存在重试，记录每次 `attempt`、`signals` 和 `decision`，不要只看最终答案。
2. 如已有失败日志，直接复用；仅当没有可用记录且设备可用时，对同一问题最多补充一次真实生成，不强制做有/无 RAG 的对照。不能凭单次结果证明资料导致问题。
3. 优先依据当前 guard 代码记录已知行为；只有复现确有必要时，在 JVM 对“罗辑一直在思考，他决心……”和“罗辑说……”做两项定向检查。日志默认不输出私人对话或原始正文。

### 阶段 2：高置信度自我旁白检测和安全重试

同时覆盖上文的视角混淆；不要仅凭出现“你”或“他”就触发重试。

1. 在 `RoleplayOutputGuard.kt` 增加独立规则 ID，例如 `self_third_person_narration`，仅在高置信度时标记 `HIGH`；保留现有 `possible_self_narration` 作为不确定情况的 `WARNING`，避免把所有 warning 全局升级为拦截。分类器依然由 observer 与 guard 共用。
2. 使用有界、可解释的规则：识别句首或明确断句后的当前角色名/已验证别名与自我思考、决定、行动、说话等谓语组合，允许“正、仍、一直、已经”等少量修饰；例如“罗辑一直在思考，他决心……”和“罗辑决定启动计划。”。避免空角色名触发泛匹配，并对每个名称使用 `Regex.escape`。若角色名只出现在“我是罗辑”“别人叫我罗辑”“罗辑是我的名字”中则不判为旁白。
3. 先识别并排除完整引文、书名等区间中的匹配；使用类似现有引号扫描的有限状态处理成对中英文引号，未闭合或嵌套时保守处理并记录不确定。不要依赖 JVM 支持而 Android ICU 不支持的正则特性；给 Android 添加覆盖。旁白中的“他说”若没有可靠主体证据，不仅凭代词触发高置信度拒绝。
4. 同一条输出可能先有第一人称再有旁白，如“我准备好了。罗辑转身离开。”；应按句局部判断，不因包含“我”就整段放行。若“罗辑”被另一个人物直接称呼，例如“史强说：‘罗辑，你还好吗？’”，或确有角色同名对象，优先避免误拦；不确定的例子只观察。
5. 沿用 `RetryWithRepair`、最多一次重试、失败后 fallback 的现有流程，专门为该 rule 加简短修复指令，要求从当前角色立场直接回答、不叙述自己；首次被拒文本不要拼回重试请求、显示或写入会话。不要让一次人称修复覆盖或绕过 `RoleplayAnswerabilityGate` 的固定安全回复；固定回复不应因为 guard 重试而变成不受 gate 约束的模型生成，必要时在 coordinator/调用层显式区分固定回复。
6. 扩展 `RoleplayOutputObserver` 和 `roleplay_observation` 的规则 ID/决策记录，记录命中次数、retry、fallback；默认不记录模型输出原文。复用当前隐私与 Debug 配置，不把试验内容写入长期记忆。
